# CareLoop产品范围草案

版本：MVP 0.1。性质：前端产品原型，非生产系统。

## 项目条件

拟由4名护理加AI专业学生推进；编程和统计基础有限。医院资源处于老师联系阶段，尚未正式对接；有潜在企业但需求尚未确认；预算未确定。计划先用1—2个月形成初版，再为2027年3—4月的参赛准备材料。具体赛事名称和官方时间仍待确认。

## 首期范围

优先验证患者新填写的一类护理产品使用体验与操作困难，围绕一个具体项目开展。产品使用场景、科室、人群和交付标准需与合作方明确，不预设普通体验问卷能够满足医学AI训练需求。

核心流程为：明确需求及相关安排 → 项目邀请 → 自愿填写 → 规则提示 → 人工复核或补充 → 范围明确的报告交付。酬谢独立处理。

## 价值假设

- 参与者：填写负担较小，允许不知道、无法评价和负面反馈。
- 项目人员：发现缺失和矛盾，降低整理成本，保留来源与处理历史。
- 企业：获得符合事先约定用途、字段和质量要求的交付，而非没有说明的记录集合。

这些价值尚需实际访谈、试点和验收反馈验证。

## 质控原则

- 参与资格、客观事实、实际行为和主观感受分别处理。
- 速度快、回答相同或负面反馈不直接等于乱填。
- 缺失、补录、协助填写和未核实字段有独立标签。
- 规则提示不自动决定数据无效或报酬取消。
- 记录原文不被复核意见覆盖，修改保留时间和原因。
- 企业报告清楚注明纳入范围、排除情况、信息来源和局限。

## 后续技术路线

1. 确认院内是否已有适合且获准使用的采集系统。
2. 若自建，优先采用简单的手机网页、Python Django和PostgreSQL，不先引入微服务。
3. 真正的服务端需要身份认证、项目及记录级授权、可靠重复校验、事务、审计、备份和受控导出。
4. 敏感信息与研究编号映射、参与记录、支付资料分别管理；部署环境由机构确认。
5. 真实采集前落实项目主体、机构数据治理、相应伦理及参与者安排、企业用途和合同。
6. AI首期可考虑使用困难文本分类或字段提取，先有规则基线与专业标注，再评价效果；按参与者隔离训练与测试。

当前原型不提供实际AI推理。可解释的规则检查不应包装成已完成机器学习研发。

## 八周里程碑

| 阶段 | 工作 | 需要产出的证据 |
| --- | --- | --- |
| 第1—2周 | 企业需求、具体科室、人群、字段与使用范围 | 需求确认表、数据字典、模拟交付样例 |
| 第3—4周 | 采集页面、项目管理、版本和权限 | 模拟流程与功能检查 |
| 第5—6周 | 质控、复核、报告、独立酬谢台账 | 可操作流程和使用反馈 |
| 第7—8周 | 技术评审和试点准备 | 修复记录、部署及责任说明 |

真实试点的启动取决于相关条件是否完成，不能由开发工期替代。

## 业务验证

先明确企业要解决的问题、接收哪些字段、使用方式、有效样本标准、验收流程和预算。按有效交付计算成本，纳入招募、报酬、复核、技术和运营时间。当前没有真实价格、合作或收入，不能在参赛材料中写作已实现。
